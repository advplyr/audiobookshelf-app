# Android Auto bookmarks

The playback service exposes a **Create bookmark** custom action for an audiobook tied to the active server account. The action saves the current whole-second position and a generated title in the native Paper database before returning. This works when the WebView is paused, the phone is locked, or the server is unreachable. A second action at the same second is ignored; bookmarks at different seconds remain independent.

The **Bookmarks** browser node shows bookmarks for the current audiobook. It overlays the JavaScript store's cached server snapshot and pending operations with native requests, so a newly created bookmark is browsable immediately. Selecting a row seeks the current playback session. The row includes the session ID; stale rows from a previous book or session cannot seek another audiobook. The list updates when a session changes, a native request is saved, or the JavaScript bookmark record changes.

The native queue is a handoff buffer, not a second server sync implementation. Each request has a UUID and server configuration ID, address, user ID, and library item ID. The JavaScript store imports only requests for its active account (including known old user IDs), persists their IDs as receipts alongside its existing offline queue, and acknowledges native requests only after that write succeeds. Repeated imports after a crash or lost acknowledgement see the receipt and do not enqueue another create. Account changes during import leave the native request intact. The existing bookmark sync logic then handles reconnection, duplicate detection, server conflicts, and retry.

At startup the app restores the last selected bookmark account. If that ID was cleared for offline mode and exactly one server configuration remains, it restores that configuration for local bookmark access without logging in or changing the selected server. With multiple saved configurations, requests stay native until the matching account is selected. Import is retried on startup, resume, reconnection, login, or a new native bookmark event. An import that cannot write Preferences leaves the native request untouched.

If a user has already edited a pending bookmark at the same second, that edit takes precedence over the native generated title. A pending deletion at the same second stays intact and the native request remains queued; neither change is silently replaced. After the deletion resolves, the next app resume or native import event can hand off the saved create. This exceptional same-position sequence may require opening the phone app again.

The native action is available only when the session matches its saved server configuration and user. A different active account prevents creation. When no account is active, a downloaded local session can still use its saved server and user identity. Native requests for other accounts remain stored until that account becomes active. No server API change is required.

For device diagnosis, filter logcat for `MediaSessionCallback`, `PlayerNotificationServ`, `AndroidAutoBookmarks`, and `AbsAudioPlayer`. A press should show which custom-action handler received it, the whole-book position in milliseconds, the native save result, and later the handoff count and acknowledgement. The WebView console logs whether import was deferred, how many native requests were found, and when an entry reached the offline store. An account mismatch or an existing bookmark at the same second is logged without exposing server addresses or credentials.

Android Gradle builds package the already copied files in `android/app/src/main/assets/public`; they do not rebuild the Nuxt app. Run `npm run generate` and `npx cap sync android` before `./gradlew :app:assembleDebug`. The Gradle prebuild check rejects web assets without the Android Auto import marker, so a native-only rebuild cannot silently ship an older WebView bundle. Install an updated APK over the existing app to retain Paper's `androidAutoBookmarks` requests. The importer reads these older requests on startup or resume and leaves each native file intact until its receipt is verified in Preferences.

If a create reached the server but its response was lost, the existing sync logic checks the server before retrying. An exact title and position match confirms the operation; a match with the same title within five seconds is presented as a possible duplicate for user resolution. It never merges based only on proximity. Without server idempotency keys, two separate clients or a changed remote bookmark can still produce an ambiguity that requires user review.

Server synchronization requires the JavaScript runtime to run with the matching authenticated account. A native request stays durable while the WebView is stopped and is imported when the app resumes, logs in, or receives the native event. Connectivity alone cannot send it to the server if Android has stopped the WebView; a native server client would duplicate authentication and conflict handling. The saved bookmark remains available in Android Auto in the meantime.
